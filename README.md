# rabbitmq

Shared RabbitMQ producer/consumer lib (`github.com/mwdev22/rabbitmq`) on top of `github.com/rabbitmq/amqp091-go`.
A service writes a `Handler` and gets at-least-once delivery, bounded retries through a TTL retry queue, a dlq, reconnects and graceful shutdown.

```sh
go get github.com/mwdev22/rabbitmq@latest
```

## usage

```go
conn, err := rabbitmq.Dial(os.Getenv("RABBITMQ_URL"))
if err != nil {
    log.Fatal(err)
}
defer conn.Close()

// producer: confirm mode, persistent, mandatory. Publish returns after the broker ack
p, err := rabbitmq.NewProducer(conn, rabbitmq.WithConfirmTimeout(5*time.Second))
defer p.Close()

e, _ := rabbitmq.NewEvent("order.created", 1, order)
err = p.PublishEvent(ctx, "orders", "order.created", e)

// consumer
c, err := rabbitmq.NewConsumer(conn, handle,
    rabbitmq.WithExchange("orders", "topic"),
    rabbitmq.WithQueue("billing.orders"),
    rabbitmq.WithRoutingKey("order.*"),
    rabbitmq.WithPrefetch(10),
    rabbitmq.WithWorkers(1),
    rabbitmq.WithRetryTTL(5*time.Second),
    rabbitmq.WithMaxRetries(3),
    rabbitmq.WithShutdownTimeout(10*time.Second),
)
defer c.Close()

ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
defer stop()
if err := c.Run(ctx); err != nil { // nil on shutdown
    log.Fatal(err) // ErrDLQ: let the orchestrator restart us, the message was requeued
}

func handle(ctx context.Context, m rabbitmq.Message) error {
    var e rabbitmq.Event
    if err := json.Unmarshal(m.Body, &e); err != nil {
        return rabbitmq.Permanent(err) // no retry, straight to dlq
    }
    return billing.Charge(ctx, m.ID, e) // other errors are retried
}
```

### options

| option | default | |
|---|---|---|
| `WithReconnectBackoff(base, max)` | 500ms / 30s | `Dial`: redial backoff after a lost connection |
| `WithConnLogger(l)` | `logging.DefaultLogger()` | `Dial` |
| `WithConfirmTimeout(d)` | 5s | producer: max wait for the broker ack |
| `WithProducerLogger(l)` | `logging.DefaultLogger()` | producer |
| `WithQueue(name)` | required | consumer: `ErrMissingQueue` without it |
| `WithExchange(name, kind)` | none, kind `topic` | consumer: declare and bind to it, otherwise consume the queue as is |
| `WithRoutingKey(key)` | `""` | consumer binding key |
| `WithRetryTTL(d)` | 5s | delay in `<queue>.retry` |
| `WithBackoff(base, max)` | off | growing per-attempt delay, capped by the retry ttl |
| `WithMaxRetries(n)` | 3 | then dlq |
| `WithPrefetch(n)` | 10 | `basic.qos` |
| `WithWorkers(n)` | 1 | concurrent handlers on one channel |
| `WithDeclare(bool)` | true | `false` when infra owns the topology |
| `WithShutdownTimeout(d)` | 10s | how long in-flight handlers get after ctx is cancelled |
| `WithConsumerLogger(l)` | `logging.DefaultLogger()` | consumer |

## semantics

**At-least-once.** A delivery is acked only after the handler returned nil, or after the message was confirmed by the broker in the retry queue or the dlq. A crash between that publish and the ack produces a duplicate, never a loss.

| situation | what happens |
|---|---|
| handler ok | ack |
| transient error, retries left | copy to `<queue>.retry` with `x-retry-count+1` (confirmed), ack |
| `Permanent(err)` or retries exhausted | copy to `<queue>.dlq` with `x-error`, `x-retry-count`, `x-original-queue` (confirmed), ack |
| retry/dlq publish fails | `Nack(requeue=true)`, `Run` returns an error wrapping `ErrDLQ` |
| ack fails (channel gone) | broker redelivers, `Run` resubscribes |
| connection lost | `Conn` redials with backoff, `Run` reopens the channel and redeclares the topology |
| ctx cancelled | stop taking messages, in-flight handlers finish (ctx detached, bounded by the shutdown timeout), ack, cancel the consumer, return nil. prefetched unacked messages go back to the queue |

The retry count comes from our own `x-retry-count` header, not `x-death`, so plain redeliveries (crash, reconnect) don't use up retries.
Retried messages keep their original routing key and exchange in `Message.Key`/`Message.Exchange` (`x-original-routing-key`, `x-original-exchange` headers).

### idempotency is the caller's job

Duplicates happen (redelivery after crash, reconnect, publish-then-ack window). `Message.ID` is stable across redeliveries and retries: the `id` header (set by `Producer` from `Event.ID`, or generated by `Publish`), else the AMQP `MessageId`. Record it in the same transaction as the side effect:

```sql
create table processed_messages (
    message_id text primary key,
    processed_at timestamptz not null default now()
);
```

```go
func (s *Service) Charge(ctx context.Context, msgID string, e rabbitmq.Event) error {
    return s.db.InTx(ctx, func(tx pgx.Tx) error {
        tag, err := tx.Exec(ctx, `insert into processed_messages (message_id) values ($1) on conflict do nothing`, msgID)
        if err != nil {
            return err
        }
        if tag.RowsAffected() == 0 {
            return nil // already processed
        }
        return s.store.CreateCharge(ctx, tx, e)
    })
}
```

## topology

Declared by the consumer on start and after every reconnect (durable, unless `WithDeclare(false)`):

```
producer ──▶ [exchange] ──routing key──▶ (queue) ──▶ consumer
                                           ▲            │
                                           │ ttl        ├─ transient, retries left ──▶ (queue.retry)
                                           └────────────┼──────────────────────────────────┘
                                                        │
                                                        └─ permanent / exhausted ─────▶ (queue.dlq)

(queue) also dead-letters broker-side rejects/expiries to (queue.dlq)
```

Retry and dlq copies are published through the default exchange keyed by queue name, so a retry lands back only in this queue, not in other queues bound to the same exchange with the same key.
No `nack(requeue=true)` loops: the retry queue is the delay.

Queue arguments are fixed at declaration. Changing `WithRetryTTL` on an existing queue fails with `PRECONDITION_FAILED`; delete `<queue>.retry` or use a new queue name.

## ordering

With `WithWorkers(1)` and a single consumer, messages are handled in queue order until a retry happens: a retried message comes back after the ttl, behind newer messages. With `WithWorkers(n > 1)` or several instances there is no ordering at all. If you need per-entity ordering, use Kafka keyed by entity ID.

`WithBackoff` uses per-message expiration. RabbitMQ only expires messages at the head of a queue, so a short delay can wait behind a longer one in `<queue>.retry`; the retry ttl still caps the total.
